# case-definition (aka casedef) — FHIR-coded case definition

Skill name is `case-definition`. The generator, valueset, and tables keep the
`casedef` alias (`casedef.py`, `casedef.csv`, `example__cohort_casedef*`).

Author the **case definition**: the special valueset that decides who is a case and
which subtype/arm they belong to. It is a `study_variable`-style coded valueset (see
the `study-variable` skill for the shared conventions) with two extra required
columns and a dedicated generator, `casedef.py`, that builds the case-matching,
longitudinal, and timeline machinery on top. Replace `example` below with your study
prefix.

Scope: this skill manages the **casedef valueset** — the codes, their subtype, and
their tier. Exclusion logic (the `cohort_casedef_exclude` stub) is out of scope here;
leave it as-is unless asked to touch it directly.

## The casedef valueset (`spreadsheet/casedef.csv`)

Required schema — **all five columns, in this order** (the file-upload declares their
`col_types`, and `casedef.py` reads the header to drive the templates):

`subtype, system, code, display, tier`

- **subtype** — the coded subtype/arm your study splits patients into. The starter
  ships placeholders (`SUBTYPE_A`, `SUBTYPE_B`); replace with your study's real arm
  labels (e.g. disease subtypes, phenotype classes). This is the root of the analytic
  subtype that flows through the case cohort into the eligible layer, so it is what
  ultimately splits the arms. Assign the most specific subtype each code implies.
  Getting it wrong misclassifies the arm — confirm it. If your study has no subtype
  distinction, use a single constant value for every row.
- **system, code, display** — the standard valueset triple (see the `study-variable`
  skill for the canonical system URIs). The case match is on `system` + `code`.
- **tier** — integer evidence specificity: `1` = a code that unambiguously
  establishes a case (and its subtype); higher tiers (e.g. `3`) = broader, adjacent,
  or supportive codes. Downstream logic favors tier-1 for establishing the case and
  its date; keep tier-1 clean.

One code per row. Unlike a generic study_variable, subtype and tier here are
**required**, not optional — every casedef row carries both.

## How the stage generates (never hand-edit the athena SQL)

`tools/casedef.py::make()` reads the casedef header (`casedef_columns()`) and renders
each `template/cohort_casedef*.sql` (Jinja, `{{ prefix }}` plus the casedef column
list) into `athena/example__cohort_casedef*.sql`, then writes `casedef.toml`. The
pipeline, in build order:

1. **file_upload** `casedef.csv` → `example__valueset_casedef`.
2. **candidate** (`cohort_casedef_candidate`) — every subject with any coded evidence
   across `study_population_{dx,rx,proc,lab,diag,doc}` whose `system` + `code` matches
   `valueset_casedef`. Carries the casedef columns (subtype, tier), the matching
   resource, and which aspect matched.
3. **exclude** (`cohort_casedef_exclude`) — a user-defined stub, currently
   `WHERE FALSE` (no exclusions). Out of scope for this skill.
4. **include** (`cohort_casedef_include`) — candidates whose subject is not in
   exclude.
5. **cohort_casedef** — the longitudinal case spine: per case subject it finds the
   first case-defining encounter, then labels every encounter `pre` / `peri` / `post`
   with `days_since` and `ordinal_since`, carrying subtype, tier, and demographics.
6. **aspects** (`cohort_casedef_{dx,lab,proc,rx}`) — the case cohort joined to each
   `study_population_<aspect>` and to `cohort_variable_union`, carrying the casedef
   columns through a `{% for col in casedef_columns %}` loop (so adding a column to
   casedef.csv flows into these automatically).
7. **timeline** (`cohort_timeline`) — casedef + all variables wide + rich encounter
   metadata.

Everything derives from `casedef.csv` and the templates, so **the human edits only
`casedef.csv`** (codes/subtype/tier). Never hand-edit
`athena/example__cohort_casedef*` or `casedef.toml`; they are generated. Structural
SQL changes belong in the `template/cohort_casedef*` sources.

## Two authoring modes — ask which up front

Same shape as `study-variable`, but every code also needs a **subtype** and a
**tier**.

**"I'm feeling lucky"** — infer the concept, pick the code systems (ICD-10-CM,
SNOMED, local for dx; the relevant systems for rx/proc/lab), and populate candidate
rows with `subtype` and `tier` filled in (specific case-defining codes at tier 1).
Present for review.

**"Clarifying questions"** — confirm before writing: the concept boundary (only
definite diagnosis codes, or include supportive procedure/med evidence?); **subtype**
per code group; tier (which codes are tier-1 case-establishing vs higher-tier
supportive); which code systems and which aspects (dx only, or also rx/proc/lab?);
inclusions/exclusions of specific codes.

In **both** modes, end with the caveat: **codes and subtype assignments are
candidates.** Verify each against an authoritative source (VSAC, ICD/SNOMED browsers)
and against the actual `core__*` data, and sanity-check subtype — a miscoded row
silently reshapes the case cohort and the subtype arms. Do not present generated
codes as validated.

## Regenerate (edit casedef.csv, then instruct — do not auto-run)

After editing `spreadsheet/casedef.csv`, tell the researcher to run, from the repo
root:

```bash
python -m cumulus_study_builder.tools.casedef
```

This re-renders `athena/example__cohort_casedef*.sql` and rewrites `casedef.toml`. A
subsequent `cumulus-library build` (or the study builder) materializes the refreshed
`example__valueset_casedef`, the candidate/include/cohort/aspect/timeline tables, and
— because subtype propagates downstream — the eligible layer. Flag that a casedef
change is high-impact: it can move who is a case and which arm.

## Relationship to study_variable

The casedef valueset is authored like any `study-variable` valueset (system, code,
display) — but subtype and tier are required, and it has its **own** generator
(`casedef.py`, not `study_variable.py`) and its own `casedef.toml`. It is
deliberately excluded from the generic variable list (`study_variable` skips names
containing `casedef`). Use this skill for the case definition; use `study-variable`
for ordinary coded variables.

## Header comment style

If you edit a `template/cohort_casedef*` source, separate sentences in prose comments
with periods, not semicolons (house style); colons are fine for labels.

## Worked examples

**Feeling lucky.** "Add the case-defining codes for arm A." → append rows to
`casedef.csv` with `subtype = SUBTYPE_A` (rename to your real label), ICD-10-CM +
SNOMED codes, tier 1 for specific codes, tier 3 for unspecified, present for review,
print the regenerate command, note verification.

**Clarifying.** "Include an indeterminate/unclassified group." → ask: which subtype
label? tier 1 or 3? dx codes only? Then add the rows with the confirmed subtype/tier
and print the regenerate command.
